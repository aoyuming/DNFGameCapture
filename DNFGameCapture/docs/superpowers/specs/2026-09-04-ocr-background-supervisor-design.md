# OCR 后台预热与自动恢复设计

## 目标

让 DNFGameCapture 在主界面完成初始化后立即后台启动并预热 Umi-OCR。用户点击“开始监控”时优先复用已经就绪的服务；监控期间如果 Umi-OCR 被关闭或本地服务掉线，后台自动恢复，不阻塞 Web、专业窗口或捕获线程。

## 根因与范围

当前实现只在点击“开始监控”后调用 `EnsureOcrRunning()`，并把本地 HTTP 服务可访问作为前置条件。自动启动使用粗粒度轮询，手动启动时则只需看到窗口出现，因此两条路径体感不同。本次只修改 OCR 生命周期，不修改捕获、识别规则、云端同步和 Web UI。

## 设计

### 后台监督线程

构造函数完成窗口、HTTP 句柄和 OCR 路径初始化后启动一个可停止的 `m_ocrSupervisorThread`。线程通过条件变量被唤醒，并按约 2 秒周期检查：

1. `Umi-OCR.exe` 进程是否存在。
2. `127.0.0.1:1224` 根接口是否可访问。
3. PaddleOCR 引擎是否已被一次最小 OCR 请求预热。

线程只通过原子状态和 `PostMessage` 与 UI 交互，所有启动、等待和 HTTP 探测都在后台完成。失败重试采用递增间隔，避免 Umi 启动失败时形成紧密拉起循环。

### 启动上下文

启动 Umi-OCR 时显式传入 `Umi-OCR.exe` 的父目录作为工作目录，并保留无焦点启动。这样自动启动与资源管理器双击使用同一资源根目录，不依赖 DNF 主进程当前工作目录。

### 预热与开始监控

后台线程发现服务可用后发送一个 1 像素 PNG 的 `/api/ocr` 请求，等待 PaddleOCR-json 返回。只有服务和引擎都就绪时才将 `m_bOcrEngineReady` 置为真。

点击“开始监控”时：

- 已就绪：立即进入现有 `StartMonitoringAfterOcrReady()`。
- 未就绪：只设置启动请求并唤醒监督线程，按钮显示启动中；就绪后由窗口消息继续原有开始流程。

监控期间的 OCR 请求失败只触发监督线程重新检查，不在 UI 线程等待或直接销毁捕获对象。

### 自动恢复

监督线程始终运行，不依赖 `m_bIsRunning`。发现 Umi-OCR 主进程消失、服务端口消失或预热状态失效时，清除就绪标记并重新执行启动流程。恢复过程中保留比分、历史战绩和捕获资源。

### 生命周期

析构和真正退出时先设置停止标志、唤醒并 `join` 监督线程，然后再关闭 WinHTTP 句柄和清理 Umi 子进程。监督线程在停止状态下不会再次拉起 OCR。

## 可观测性

日志记录以下阶段及耗时：

- 请求后台预热。
- `ShellExecuteEx` 成功返回。
- Umi 进程/服务就绪。
- PaddleOCR 引擎预热完成或失败。
- 检测到关闭并开始恢复。

## 验收标准

- 主程序启动后不阻塞，Umi-OCR 在后台自动启动。
- 通常情况下点击“开始监控”不再等待 OCR 启动。
- 手动关闭 Umi-OCR 后约数秒内自动重新拉起。
- 自动启动使用正确工作目录，服务探测和预热不运行在 UI 线程。
- 程序退出后无监督线程访问已销毁对象。
- 原有监控、OCR、捕获和 Web 状态流程保持兼容。
