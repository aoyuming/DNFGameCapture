# 共享选手库冲突源头治理与批量确认设计

**日期：** 2026-09-12
**状态：** 待用户评审
**适用版本：** 5.2.2

## 1. 背景

5.2.1 已把 V2 自动同步顺序改为“先拉取公共库、落库成功后再基于最新快照投稿”，从源头避免其他主播用旧本地身份编号重复投稿而产生大批名称归属冲突。

公共库与本地库确实存在不同归属时，5.2.1 会跳过冲突选手并暂停本轮自动投稿。这能避免把部分导入后的混合快照继续送入审核区，但也带来两个问题：服务器看不到本轮本地冲突证据；管理员只能等待主播手动投稿或逐条修改已有待审记录。

现有服务器已经支持单条待审记录关联公共选手、公共实体手动合并和旧编号重定向。本设计在这些能力上增加冲突上报、服务器聚合和一次性批量确认，不改变名称冲突必须由管理员确认的安全边界。

## 2. 目标与非目标

### 目标

- 保留 5.2.1 的“先拉取、后投稿”顺序，防止旧问题重新出现。
- 拉取发生真实归属冲突时，把最新本地证据送入服务器待审核区，而不是静默停止。
- 按冲突连通组聚合多个主播、多个投稿中的重复问题。
- 对只对应一个现有公共选手的投稿实体生成批量关联建议。
- 允许管理员在一个预览中勾选多组并一次确认，不必逐条打开投稿。
- 对已经存在于公共库的多个实体，允许每组明确选择保留对象后随同批次合并。
- 确认后保留名称和游戏 ID 并集，建立旧 ID 到保留 ID 的永久重定向。
- 客户端下次拉取重定向后自动解除本地冲突并恢复正常投稿。
- 整批操作具备版本保护、事务回滚、幂等和审计记录。

### 非目标

- 不按同名直接自动合并。
- 不把多个可能目标自动压成一个人。
- 不改变“至少 5 个共同游戏 ID 才自动归并”的现有规则。
- 不把游戏 ID 共用本身视为归属冲突。
- 不删除原投稿、公共名称、游戏 ID、比赛数据或本地身份组。
- 不在本次改动中部署正式服务器或自动修改真实公共库。

## 3. 核心原则

1. **源头预防优先。** 正常客户端始终先拉取并导入公共身份，再生成投稿快照。
2. **自动发现，人工定案。** 服务器可以计算唯一候选，但只有管理员明确确认后才能改变身份归属。
3. **按身份组处理。** 一个选手的名称和游戏 ID 不拆开分别通过。
4. **重定向闭环。** 仅修改待审目标不够；确认后的旧投稿 ID 必须重定向到公共保留 ID，使产生冲突的客户端能够自愈。
5. **一次事务。** 批量公共合并、待审关联、增量发布、重定向、投稿状态和审计要么全部成功，要么全部不变。

## 4. 总体数据流

```text
客户端启动
  -> 拉取公共库
  -> 本地导入
     -> 无冲突：用导入后的快照正常投稿
     -> 有冲突：保留冲突本地实体，用导入后的快照投稿并标记待确认
  -> 服务器按现有幂等签名创建或复用待审投稿

管理后台
  -> 汇总全部待审冲突
  -> 生成唯一目标关联建议和公共实体合并组
  -> 管理员预览、勾选、选择保留对象、一次确认
  -> 服务器在一个事务中发布并建立重定向

客户端下次同步
  -> 拉取新公共版本和 entityRedirects
  -> 将旧编号解析为保留编号
  -> 冲突消失，正常自动投稿
```

## 5. 客户端行为

### 5.1 部分拉取后继续上报

`QueuePlayerLibraryImport` 仍以 `skipOwnershipConflicts=true` 导入公共库。若 `importReport.skipped` 非空：

- 保留 `libraryPartial=true`，不把本轮记录为七天同步成功。
- 从已经持久化的最新 `PlayerLibrarySnapshot::v2Entities` 重新构造投稿，不能使用拉取前缓存。
- 调用现有 V2 投稿接口。公共库已有且无变化的实体由服务器去重；本地冲突实体进入待审核区。
- 投稿成功或已经待审时，界面显示“冲突资料已送后台，等待管理员批量确认”，而不是“已暂停自动投稿”。
- 网络失败仍按失败处理，下次启动重试；不得把未送达说成待确认。

### 5.2 重试和记账

- 部分拉取即使上报成功，也不更新七天成功检查点。
- 同一快照通过服务器待审签名和客户端 push tracker 保持幂等，不重复生成投稿。
- 当前运行周期不循环重试；管理员处理后可重启客户端，或关闭再开启自动同步，立即重新拉取。
- 完整拉取成功且后续投稿成功或无变化后，才恢复正常七天检查点。

## 6. 服务器冲突聚合

服务器在读取后台状态时，基于当前公共实体、规范化后的待审实体和 `entityRedirects` 构造名称归属冲突图。节点为规范化后的实体 ID，边为同一规范化名称被不同实体占用。

每个连通组只生成一个后台条目，并聚合：

- 涉及的公共实体及其名称、游戏 ID。
- 涉及的待审来源实体、投稿编号和主播设备数量。
- 造成冲突的名称。
- 每条待审记录的 `submissionRevision`。
- 可执行类型和不能批量处理的原因。

### 6.1 唯一目标关联建议

只有同时满足以下条件才生成默认可勾选的“关联现有选手”建议：

- 冲突组中恰好有一个当前有效的公共实体。
- 每个待审来源 ID 尚未重定向到其他目标。
- 来源 ID 没有在另一个冲突组指向不同目标。
- 合并整个来源实体后不会产生新的组外名称冲突。
- 投稿格式、数组上限和公共库最终投影均有效。

名称相同只是生成建议的依据，不会绕过管理员确认。

### 6.2 公共实体合并组

冲突组包含两个或更多当前公共实体时，不自动选择目标。后台要求管理员在该组内明确选择一个保留 ID，随后才能勾选进批次。未选择目标的组保持待处理。

一个批次中若同一实体被要求指向不同目标，预览和提交均拒绝。重定向链在提交前展平，并拒绝循环、缺失目标和已退役 ID 复活。

## 7. 批量确认接口

后台状态响应新增 `conflictResolutionGroups`，由服务器根据当前数据生成，不信任浏览器自行推断。每组包含稳定的预览摘要和基于以下内容计算的校验令牌：

- 当前公共库 revision。
- 涉及投稿的 ID 与 `submissionRevision`。
- 来源 ID、目标 ID 和冲突名称集合。

新增管理员接口：

```text
POST /admin/api/library/conflicts/resolve
```

请求包含：

- 当前公共库 `revision`。
- 管理员选中的组及服务器签发的组令牌。
- 公共实体合并组中明确选择的 `targetEntityId`。
- `confirm: true`。

接口继续使用现有管理员认证、CSRF、防请求体过大和限流边界。任何 revision、投稿版本、组令牌或目标状态过期时，整批返回 `409`，后台刷新预览，不执行部分旧决定。

## 8. 事务处理

批量接口在一个 SQLite immediate transaction 中：

1. 重新读取公共库和所有涉及的待审投稿。
2. 重新计算冲突组并逐项核对请求令牌。
3. 保存尚未留底的原始投稿到 `player_library_submission_originals`。
4. 对公共实体合并组计算名称和游戏 ID 并集，并确定退役 ID。
5. 将唯一目标待审实体的全部字段增量并入目标实体。
6. 为所有非保留来源 ID 写入展平后的 `player_entity_redirects`；当前公共实体来源先从最终投影移除，再写重定向。
7. 对已解决的投稿实体标记通过；同一投稿中未选中或仍有歧义的实体继续保持 pending。
8. 对最终完整投影重新执行名称唯一性、自动归并证据、大小和引用完整性校验。
9. 公共库只增加一次 revision，并写入批量冲突处理审计。

新增审计记录保存操作者可追溯的数据：批次时间、发布 revision、所选组、来源到目标映射、处理前公共实体、处理后公共实体、受影响投稿及原始重定向。审计只追加，不覆盖原投稿留底。

## 9. 后台界面

共享库审核页增加“冲突批量处理”区域：

- 顶部显示可批量关联、需选择公共保留对象、仍有歧义三类数量。
- 唯一目标建议默认勾选，可展开查看冲突名称、投稿来源和双方全部游戏 ID。
- 公共实体合并组必须先选择保留对象，才允许勾选。
- 支持全选可安全确认项、清空选择和关键词筛选。
- 提交前使用一个确认对话框汇总“处理组数、关联投稿实体数、合并公共实体数、将建立的重定向数”。
- 成功后显示接受、仍待审和公共库新 revision；过期时自动刷新并提示重新核对。

现有逐条编辑、单组公共合并和部分审核继续保留，作为歧义项的细粒度入口。

## 10. 兼容性与发布顺序

- 先部署 5.2.2 服务器和后台，再发布 5.2.2 客户端。
- 5.2.1 客户端继续按原逻辑暂停，不会因服务器升级改变行为。
- 5.2.2 客户端沿用现有投稿 API，因此服务器升级期间不会产生未知请求格式。
- 旧待审投稿无需删除或重传；服务器升级后会直接纳入冲突聚合。
- 数据库迁移只新增审计结构，不改写现有公共实体、投稿和重定向。
- 正式服部署、真实批量确认和客户端分发必须由用户另行明确授权。

## 11. 验收测试

### 客户端

- 部分拉取后使用落库后的新快照投稿，而不是拉取前快照。
- 部分拉取上报成功时显示待管理员确认，但不写七天成功检查点。
- `already_pending` 不创建重复投稿。
- 上报失败、生命周期失效、授权范围改变和关闭自动同步时不误报成功。
- 拉取到管理员建立的重定向后，原冲突实体能够完整导入并恢复正常自动投稿。

### 服务器

- 多个投稿指向同一公共实体时聚合为一个唯一目标建议。
- 一个确认批次可处理多组、多个投稿，并只增加一次公共 revision。
- 批量关联保留全部名称和游戏 ID，原投稿字节级留底不变。
- 来源 ID 建立永久重定向，重复提交解析到保留 ID。
- 多公共目标、跨组矛盾、循环映射和组外新冲突不能作为唯一目标批量通过。
- 任一 stale revision、stale submission、审计失败或数据库写入失败整批回滚。
- 未选中和仍有歧义的实体继续 pending，已确认的无冲突实体不再出现。

### 后台

- 预览准确显示组数、来源、目标、冲突名称和字段并集。
- 唯一目标建议可一次全选确认。
- 公共实体组未选择保留对象时无法提交。
- 二次确认、CSRF、忙碌态、过期刷新和成功结果均可通过浏览器回归测试。

## 12. 成功标准

- 5.2.2 正常同步不再重现 5.2.0 的拉取前批量投稿冲突。
- 当前这类真实拉取冲突会自动出现在服务器批量处理区。
- 管理员可以一次确认所有唯一目标项，而不是逐条修改投稿。
- 确认后的客户端通过重定向自愈，无需手动重新建立选手或逐条投稿。
- 系统仍不会在无人确认时仅凭同名合并两位选手。
